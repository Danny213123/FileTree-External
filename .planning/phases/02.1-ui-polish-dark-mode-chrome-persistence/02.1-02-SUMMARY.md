# Phase 02.1 Plan 02: Settings.active_tab Persistence Summary

Adds `Settings.active_tab: String` (default `"details"`) with full JSON round-trip and three new unit tests, following the locked 4-edit column-widths pattern from Plan 02-05 — pure persistence-layer change with zero UI wiring (that lands in 02.1-04/05).

## Goal

Close the settings layer for D-13 (active-tab persistence) as a strict prerequisite for Plan 02.1-04. Old `settings.json` files without the key must load cleanly with `active_tab == "details"`; new files must round-trip any string value intact.

## What Changed

### Edit 1 — Struct field (src/settings.rs:26)

```rust
pub(crate) active_tab: String,
```

Placed AFTER `window: WindowGeometry,` and BEFORE `unknown: BTreeMap<String, RawJsonValue>,` per PATTERNS.md placement note.

### Edit 2 — Default impl (src/settings.rs:45)

```rust
active_tab: "details".to_string(),
```

Adjacent to other field initializers in the same order as the struct.

### Edit 3 — Writer block in `push_settings_json` (src/settings.rs:231–232)

```rust
output.push_str(",\"active_tab\":");
crate::export::push_json_string(output, &settings.active_tab);
```

Lands immediately after the `window` object closing `}` and immediately before the unknown-keys round-trip loop. Reuses the existing JSON escape helper.

### Edit 4 — Reader match arm in `parse_top_object` (src/settings.rs:383–388)

```rust
"active_tab" => {
    let v = parse_value(bytes, pos, 1)?;
    if let RawJsonValue::Str(s) = v {
        settings.active_tab = s;
    }
}
```

Matches the exact shape of the existing `"last_path" =>` arm. Unknown keys continue to fall through to the existing `_ =>` unknown bucket.

### Edit 5 — Three unit tests (src/settings.rs:1004–1047)

- `active_tab_default` (lines 1006–1010): asserts `Settings::default().active_tab == "details"`.
- `active_tab_roundtrip` (lines 1012–1039): constructs a Settings with `active_tab = "errors"`, serializes, asserts the substring `"active_tab":"errors"` appears in the output, parses back, asserts the field plus every other known field round-trip unchanged.
- `backward_compat_no_active_tab` (lines 1041–1046): parses a minimal `{"schema_version":1,"dark_mode":true}` literal (no `active_tab` key), asserts `parsed.active_tab == "details"` and `parsed.dark_mode == true`.

### Compatibility-shim Edit — pre-existing test (src/settings.rs:829, 846)

The `round_trip_all_known_fields` test constructs `Settings { ... }` via explicit struct literal — adding a new field forces a one-line addition (`active_tab: "details".to_string(),`) and one new assertion (`assert_eq!(parsed.active_tab, original.active_tab)`). The plan called out this exact predicted fix-up in `<action>` paragraph 6.
