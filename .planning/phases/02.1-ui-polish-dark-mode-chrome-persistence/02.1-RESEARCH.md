## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Icon source = embed `bootstrap-icons.ttf` (TrueType, ~120 KB) under `assets/bootstrap-icons-1.11.3.ttf` via `include_bytes!`, register at startup with `AddFontMemResourceEx`. Render glyphs via `DrawTextW` using Private Use Area codepoints. Monochrome only. GDI does NOT accept `.woff` / `.woff2` — must download the `.ttf` build from the Bootstrap Icons GitHub releases page, NOT the npm `.woff2`. License: MIT (record in NOTICE/about box).
- **D-02:** Icon placement is **content tab headers only** this phase. No tree-row, menu-item, or status-bar icons.
- **D-03:** Dark-mode strategy = undocumented uxtheme APIs first, owner-draw only where they fail. Resolve via `GetProcAddress` with null-check: ordinal **135** `SetPreferredAppMode(AllowDark)`, ordinal **133** `AllowDarkModeForWindow(hwnd, TRUE)`, ordinal **136** `FlushMenuThemes`. Per-control `SetWindowTheme(hwnd, L"DarkMode_Explorer", NULL)`. Owner-draw required for menu bar and status footer.
- **D-04:** Dark applied **before** `CreateWindowExW` for the main window and all children. Order: read `settings.dark_mode` → `SetPreferredAppMode` → create window → `DWMWA_USE_IMMERSIVE_DARK_MODE` (before first `ShowWindow`). Children inherit theme on creation → no first-paint flash.
- **D-05:** Color palette = system accent + tuned grayscale surface. Accent from `DwmGetColorizationColor` on launch + `WM_DWMCOLORIZATIONCOLORCHANGED`. Dark `#1e1e1e` bg, `#2d2d2d` controls, `#cccccc` text, `#3a3a3a` hairlines; light keeps current GDI sysColors. Selection = accent fill + white text (with luminance fallback to black if accent luminance > 0.6).
- **D-06:** Delete the current toolbar row (Hidden / Files / Dark checkboxes). Move toggles into the **View menu** as `MF_CHECKED` items. Sync via `WM_INITMENUPOPUP`.
- **D-07:** Apple-HIG-ish, compact + dense. Segoe UI Variable Text 9pt; row height 22 px; 1 px hairlines (#3a3a3a dark / #e5e5e5 light); no zebra striping; accent fill + white text for selection; no rounded corners; no drop shadows; no 3D etched/sunken styles.
- **D-08:** TreeSize-style **content tabs** — 5 tabs: Details / Top / Extensions / Duplicates / Errors. Layout: path bar → tab strip → content panel → status bar. Tab strip is custom-painted (owner-draw, NOT `SysTabControl32`), 28–32 px tall. Each tab: bootstrap-icon glyph + label, accent underline under active tab, no boxes/borders/backgrounds.
- **D-09:** **Keep the system titlebar.** Only behavior is `DwmSetWindowAttribute(DWMWA_USE_IMMERSIVE_DARK_MODE, TRUE)` before first `ShowWindow`. No `DwmExtendFrameIntoClientArea`, no custom caption buttons, no Mica.
- **D-10:** First-paint flash fix — covered by D-04 ordering.
- **D-11:** **Drive-picker restore.** After `populate_drive_picker`, parse drive letter from `settings.last_path` and call `CB_SETCURSEL`. Falls back to `C:`.
- **D-12:** **View-menu state sync.** Handle `WM_INITMENUPOPUP` reading current `settings` snapshot; call `CheckMenuItem(..., MF_CHECKED|MF_UNCHECKED)`.
- **D-13:** **Active tab persistence.** New `settings.json` field `active_tab: "details"|"top"|"extensions"|"duplicates"|"errors"`, default `"details"`. Restored on launch by routing tab-switch command after window creation. Save-on-tab-switch is discrete (no coalesce; write immediately). Unknown-keys round-trip from Phase 02 D-02 protects forward compat.

### Claude's Discretion

- **Menu-bar owner-draw scope.** `WM_MEASUREITEM` + `WM_DRAWITEM` for top-level + popup items. `GetMenuInfo`/`SetMenuInfo` with `MIM_BACKGROUND`. Separators drawn by GDI with a thin themed pen — not owner-drawn.
- **Status-bar owner-draw scope.** Replace `msctls_statusbar32` with a simple custom-painted footer (single window, computes 5 panes in `WM_PAINT`, reuses `format_status_*` from `paint.rs`).
- **Tab strip implementation.** New `src/desktop/tabs.rs`: owner-paints the strip, handles `WM_LBUTTONDOWN` → tab switch → `PostMessage(WM_COMMAND, ID_TAB_<NAME>)`. State (`active_tab`) lives on `DesktopState`. Content swap = show/hide one of 5 child container HWNDs.
- **Icon-font lookup helper.** New module `src/desktop/icons.rs`: const codepoint constants + `draw_icon(hdc, x, y, codepoint, size_px, color)` helper.
- **Accent color caching.** Read `DwmGetColorizationColor` once on launch; cache on `DesktopState.accent_color`; invalidate + repaint on `WM_DWMCOLORIZATIONCOLORCHANGED`. Don't query per paint.
- **Fallback for missing uxtheme ordinals.** If `GetProcAddress("uxtheme.dll", 135)` returns null, dark-mode toggle still flips palette + `DWMWA_USE_IMMERSIVE_DARK_MODE`; just no dark scrollbar/combobox skin. Log via `eprintln!` in debug only.
- **High-DPI.** Per-monitor-aware (Phase 1 setup). Recreate fonts on `WM_DPICHANGED`.

### Deferred Ideas (OUT OF SCOPE)

- Auto-follow system dark/light (tri-state with `WM_SETTINGCHANGE` "ImmersiveColorSet" watcher).
- `DwmExtendFrameIntoClientArea` / custom titlebar buttons / Mica backdrop.
- Tree-row leading icons, menu-item leading icons, status-bar icon prefixes.
- Embedded non-system typography (Inter font etc.).
- Drop the menu bar entirely / Options window replacing it.
- Tab-content for Top / Extensions / Duplicates / Errors panels (02.1 ships the strip + persisted active tab + Details binding + "Coming soon" placeholders only).
- Ctrl+Tab / Ctrl+Shift+Tab tab cycling (Ctrl+1..5 jumps remain in scope; cycling is OK-to-defer).

## Project Constraints (from CLAUDE.md)

- **Zero new Rust crates.** `Cargo.toml [dependencies]` stays empty by design. Any new dependency is a Key Decision requiring rationale. (02.1 ships zero new crates — all FFI is hand-written.)
- **No `build.rs`.** Icon font is a static binary asset (`assets/bootstrap-icons-1.11.3.ttf` committed to repo), not a generated one.
- **Native UI via raw Win32 FFI only.** `User32`, `Gdi32`, `Shell32`, `Comctl32`, `Dwmapi`, `Ole32`, `UxTheme`, `Kernel32`, `Shlwapi`. No GUI toolkit (no Tauri / egui / iced).
- **Web assets embedded at compile time via `include_str!`.** No bundler, no npm. The same posture applies to the icon font: `include_bytes!("../../assets/bootstrap-icons-1.11.3.ttf")`.
- **Single standalone `.exe`** — no installer, no auto-update, no telemetry.
- **Windows 10/11** for the desktop surface. (Phase 02.1 is desktop-only; `serve` and `scan` modes unaffected.)
- **GSD workflow enforcement.** All Edit/Write operations go through a GSD command (this research is part of `/gsd-research-phase`).
- **Naming conventions.** `snake_case` for Rust fns/locals; `PascalCase` for types; Win32 constants in `UPPER_SNAKE_CASE` matching Win32 names exactly (`WM_INITMENUPOPUP`, `MF_CHECKED`, `MIM_BACKGROUND` — don't anglicize). `push_*` for `&mut String` builders, `*_to_*` for serializers, `is_*`/`has_*`/`should_*` for predicates.
- **Error handling.** `io::Result<T>` propagated up to entry points with `?`. `.expect("... lock poisoned")` on Mutex. No `unwrap()` outside tests.
- **GDI double-buffering** for any custom-painted surface (existing `paint.rs` pattern is the model).

## Summary

This phase is a focused Win32 visual-cohesion pass: close the dark-mode chrome gap across every control, replace the 4-checkbox toolbar with a TreeSize-style 5-tab content strip + View menu, embed Bootstrap Icons as a static TTF asset for the tab glyphs, and close four persistence gaps (first-paint flash, drive-picker restore, View-menu sync, new `active_tab` field). All implementation is hand-written Win32 FFI atop the existing `src/desktop/` module split (confirmed: directory module, NOT inline — see Codebase Orientation below).

**Codebase orientation correction.** The agent invocation prompt described the desktop module as "currently inline in `src/main.rs` (the `mod desktop { ... }` block)." This is **stale**. Phase 1 (module split, 3/3 plans complete) already extracted the desktop subsystem into a directory module: `src/desktop/{ffi.rs, mod.rs, paint.rs, shell.rs, state.rs, tabs.rs, theme.rs, treemap.rs}`. Plan against the directory layout. `tabs.rs` and `treemap.rs` are 1-line stub placeholders from the split — `tabs.rs` is where the new tab-strip window class lands.

**Theme.rs is the linchpin.** It already has `DARK_BRUSH` / `LIGHT_BRUSH` `OnceLock<Hbrush>`, `DARK_MODE_ATOMIC: AtomicBool`, `apply_theme(state)` calling `SetWindowTheme("DarkMode_Explorer")`, and (critically) `set_window_dark_mode` already sets `DWMWA_USE_IMMERSIVE_DARK_MODE` using BOTH attribute values 20 AND 19 — the correct cross-version approach (one succeeds for builds ≥19041, the other for 17763–18363). Phase 02.1 **extends** theme.rs (palette constants, accent caching, uxtheme ordinal resolver, owner-draw color helpers) — does NOT replace it. **One known palette divergence:** current `palette_bg` returns `rgb(12,13,15)`; D-05 spec mandates `#1e1e1e` = `rgb(30,30,30)`. The plan must rewrite the palette constants to D-05 values.

**Primary recommendation:** Land the 6 work units in dependency order: (1) `assets/bootstrap-icons-1.11.3.ttf` + `icons.rs` codepoint module + `AddFontMemResourceEx` registration in startup, (2) extend `theme.rs` with D-05 palette + accent cache + uxtheme ordinal resolver, (3) extend `ffi.rs` with the missing API declarations (full gap list below), (4) `settings.rs` `active_tab` round-trip following the 02-05 column-widths pattern, (5) `mod.rs` rewire: delete toolbar checkbox creation, add menu construction, add `WM_INITMENUPOPUP` + `WM_DWMCOLORIZATIONCOLORCHANGED` + `WM_DRAWITEM` + `WM_MEASUREITEM` + `WM_DPICHANGED` arms, add 5 new tab-jump accelerators, (6) `tabs.rs` window class + 5 content panel HWNDs + active-tab restore on launch + custom status footer in `paint.rs::draw_status_footer`.

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Bootstrap Icons TTF | Embedded SVG decoded at runtime | Requires an SVG parser (zero-dep posture forbids `usvg`/`resvg`); hand-rolling one is far more code than `AddFontMemResourceEx`. **Rejected.** |
| Bootstrap Icons TTF | Pre-rendered PNG sprites per DPI | Multiple bitmaps per glyph, breaks at custom DPIs; TTF is DPI-free. **Rejected.** |
| Bootstrap Icons | Fluent UI System Icons or Lucide TTF | Bootstrap Icons is more consistent in stroke weight at small sizes; CONTEXT D-01 locked this. **Locked.** |
| Custom-painted tab strip | `SysTabControl32` native control | D-08 rejects — hard to dark-theme cleanly, looks dated. **Locked.** |
| Custom-painted status footer | `msctls_statusbar32` with `SBT_OWNERDRAW` per pane | Possible but the common control's frame/sizing-grip ignore the dark hint anyway; replacing it wholesale is simpler. **Locked per Discretion.** |
| Owner-draw menu | `BCM_SETSHIELD`-style themed buttons in a `ReBar` | Loses Alt-key activation, mnemonic underlines, accelerators, accessibility. **Rejected.** |
| Undocumented uxtheme ordinals | Hand-roll dark scrollbar/combobox from scratch | Thousands of lines of GDI; the ordinals exist for exactly this. **Rejected** in favor of D-03's "ordinals first, owner-draw only where they fail." |

### Pattern 1: Uxtheme Ordinal Resolution (one-time cached)

**What:** Resolve undocumented uxtheme exports via `GetProcAddress` with `MAKEINTRESOURCEA(ordinal)`, cache function pointers in a `OnceLock<UxthemeOrdinals>`, null-check before each call.
**When to use:** Once at startup, before any window creation. Cached pointers live on `DesktopState` (or a `theme.rs` `OnceLock`).
**Example:**

```rust
// In src/desktop/theme.rs (NEW)
use std::sync::OnceLock;

#[repr(i32)]
#[derive(Copy, Clone)]
pub enum PreferredAppMode {
    Default = 0,
    AllowDark = 1,
    ForceDark = 2,
    ForceLight = 3,
    Max = 4,
}

type FnSetPreferredAppMode = unsafe extern "system" fn(PreferredAppMode) -> PreferredAppMode;
type FnAllowDarkModeForWindow = unsafe extern "system" fn(Hwnd, i32) -> i32; // BOOL
type FnFlushMenuThemes = unsafe extern "system" fn();

pub struct UxthemeOrdinals {
    pub set_preferred_app_mode: Option<FnSetPreferredAppMode>,
    pub allow_dark_mode_for_window: Option<FnAllowDarkModeForWindow>,
    pub flush_menu_themes: Option<FnFlushMenuThemes>,
}

static UXTHEME: OnceLock<UxthemeOrdinals> = OnceLock::new();

pub fn uxtheme_ordinals() -> &'static UxthemeOrdinals {
    UXTHEME.get_or_init(|| unsafe {
        let module = LoadLibraryW(w_str!("uxtheme.dll").as_ptr());
        if module.is_null() {
            return UxthemeOrdinals { set_preferred_app_mode: None, allow_dark_mode_for_window: None, flush_menu_themes: None };
        }
        // MAKEINTRESOURCEA(n) is just (n as usize as *const u8) — the cast to LPCSTR
        let resolve = |ord: u16| -> *mut std::ffi::c_void {
            GetProcAddress(module, ord as usize as *const i8)
        };
        let p135 = resolve(135);
        let p133 = resolve(133);
        let p136 = resolve(136);
        UxthemeOrdinals {
            set_preferred_app_mode:     if p135.is_null() { None } else { Some(std::mem::transmute(p135)) },
            allow_dark_mode_for_window: if p133.is_null() { None } else { Some(std::mem::transmute(p133)) },
            flush_menu_themes:          if p136.is_null() { None } else { Some(std::mem::transmute(p136)) },
        }
    })
}

// Source: wxWidgets src/msw/darkmode.cpp (same ordinals, production use)
```

### Pattern 3: Embedded TTF Registration

**What:** `include_bytes!` the .ttf, hand the static slice to `AddFontMemResourceEx`. Store the returned `HANDLE` for the lifetime of the process (or call `RemoveFontMemResourceEx` at shutdown). Font is then usable by family name (`"bootstrap-icons"`) in any subsequent `CreateFontIndirectW` / `LOGFONTW`.
**When to use:** Once at startup, before any tab strip paint. Lifetime: keep the handle alive for the entire process; the static slice from `include_bytes!` has `'static` lifetime by construction (the data lives in the .exe's read-only segment), so no UB.
**Example:**

```rust
// In src/desktop/icons.rs (NEW)
static ICON_FONT_BYTES: &[u8] = include_bytes!("../../assets/bootstrap-icons-1.11.3.ttf");
static ICON_FONT_HANDLE: OnceLock<*mut c_void> = OnceLock::new();

pub fn register_icon_font() {
    ICON_FONT_HANDLE.get_or_init(|| unsafe {
        let mut num_fonts: u32 = 0;
        let handle = AddFontMemResourceEx(
            ICON_FONT_BYTES.as_ptr() as *const c_void,
            ICON_FONT_BYTES.len() as u32,
            std::ptr::null_mut(),
            &mut num_fonts as *mut u32,
        );
        if handle.is_null() {
            eprintln!("AddFontMemResourceEx failed; icon font unavailable");
        }
        handle
    });
}
// Source: learn.microsoft.com/windows/win32/api/wingdi/nf-wingdi-addfontmemresourceex
// The returned HANDLE is opaque; the font is auto-removed when the process exits.
// We never call RemoveFontMemResourceEx (process-lifetime registration).
```

**Pitfall:** `AddFontResourceExW` (no "Mem") writes a temp file. We want the **Mem** variant — no filesystem write, no install footprint.

### Pattern 5: Owner-Draw Menu Item

**What:** Build the menu with `MF_OWNERDRAW`; respond to `WM_MEASUREITEM` (set cx/cy of the item rect) and `WM_DRAWITEM` (paint via the `DRAWITEMSTRUCT->hDC` into `rcItem`).

**Example:**

```rust
    let dis = &*dis;

        state.accent_color
    } else {
        palette_panel(state)
    };

    } else {
```

### Pattern 7: DwmGetColorizationColor + WCAG Luminance + WM_DWMCOLORIZATIONCOLORCHANGED

**What:** Query system accent once at startup, cache; recompute selected-text color via WCAG luminance (threshold 0.6 per D-05 + UI-SPEC); invalidate on color change.
**When to use:** Once at startup AND on every `WM_DWMCOLORIZATIONCOLORCHANGED` message.
**Example:**

```rust
// In src/desktop/theme.rs (NEW)
pub fn refresh_accent(state: &mut DesktopState) {
    let mut color: u32 = 0;
    let mut opaque_blend: i32 = 0;
    unsafe {
        DwmGetColorizationColor(&mut color as *mut u32, &mut opaque_blend as *mut i32);
    }
    // DwmGetColorizationColor returns ARGB. Strip alpha; convert to COLORREF (BGR).
    let a_stripped = color & 0x00FFFFFF;
    let r = ((a_stripped >> 16) & 0xFF) as u8;
    let g = ((a_stripped >>  8) & 0xFF) as u8;
    let b = ( a_stripped        & 0xFF) as u8;
    state.accent_color = rgb(r, g, b);  // BGR-encoded COLORREF
    state.selected_text_color = selected_text_for_accent(r, g, b);
}

fn selected_text_for_accent(r: u8, g: u8, b: u8) -> u32 {
    // WCAG relative luminance, threshold 0.6 (locked per UI-SPEC).
    let rf = (r as f32) / 255.0;
    let gf = (g as f32) / 255.0;
    let bf = (b as f32) / 255.0;
    let lum = 0.2126 * rf + 0.7152 * gf + 0.0722 * bf;
    if lum > 0.6 { rgb(0, 0, 0) } else { rgb(255, 255, 255) }
}

// In window_proc:
WM_DWMCOLORIZATIONCOLORCHANGED => {
    with_state_mut(|state| {
        refresh_accent(state);
        InvalidateRect(state.hwnd, std::ptr::null(), 1 /* TRUE */);
    });
    return 0;
}
// Source: learn.microsoft.com/windows/win32/api/dwmapi/nf-dwmapi-dwmgetcolorizationcolor
// Source: learn.microsoft.com/windows/win32/dwm/wm-dwmcolorizationcolorchanged
// Source: WCAG 2.x relative luminance formula
```

### Anti-Patterns to Avoid

- **Inline-paint without double-buffering.** Existing `paint.rs` uses CreateCompatibleDC + BitBlt — every new custom-paint surface (tab strip, menu items, status footer) MUST follow suit. Single-buffered paint flickers on resize.
- **Calling `DwmGetColorizationColor` from `WM_PAINT`.** Cache it on `DesktopState`; refresh only on `WM_DWMCOLORIZATIONCOLORCHANGED` (per CONTEXT Discretion).
- **Hard-coding glyph codepoints in painter code.** All Bootstrap Icons codepoints live in `src/desktop/icons.rs` constants — never in paint.rs or tabs.rs directly.
- **`AddFontResourceExW` (no "Mem") with a `tempfile`.** Always use `AddFontMemResourceEx`; the temp-file variant pollutes the user's temp dir and is the wrong tool.
- **Calling `SetPreferredAppMode` after `CreateWindowExW`.** D-04 explicitly orders this before window creation. Calling after means children render light, then snap to dark — that's the "first-paint flash" D-10 fixes.
- **Owner-drawing menu separators.** Per Discretion: let GDI's themed pen draw them. Adding `MF_OWNERDRAW` to separators forces the painter to special-case them and gain nothing visually.
- **Reading `settings.dark_mode` from `WM_PAINT`.** Use `DARK_MODE_ATOMIC` (existing pattern in theme.rs) — atomic load is cheaper than the `with_state_mut` lock acquire, and paint paths must not block on the state mutex.
- **Querying `GetDpiForWindow` per paint.** Cache the DPI snapshot on `DesktopState.current_dpi`; update on `WM_DPICHANGED` only.
- **Mutating settings inside `with_state_mut` and saving before the lock releases.** Always: snapshot inside closure → drop the guard → call `save_settings_if_dirty` outside. The Phase 02 column-widths gap (`flush_pending_persist` not reading widths) is partly because the snapshot/save dance is subtle — re-read state.rs before extending.

The zero-dep posture does NOT mean hand-rolling system functionality — it means not adding Rust crates. Win32 itself is the platform; use it fully.

## Common Pitfalls

### Pitfall 1: First-Paint Flash if Dark Applied After ShowWindow

**What goes wrong:** Window appears in light theme for ~16 ms, then snaps dark.
**Why it happens:** `SetPreferredAppMode(AllowDark)` only affects newly-created children; if called after `CreateWindowExW`, the just-created children rendered light first. Same for `DWMWA_USE_IMMERSIVE_DARK_MODE` — if set after `ShowWindow`, the titlebar paints light first.
**How to avoid:** Strict ordering per D-04: `SetPreferredAppMode` in `cli.rs::run_desktop` BEFORE `desktop::run`. Inside `desktop::run`: `CreateWindowExW(main)` → `DwmSetWindowAttribute(IMMERSIVE_DARK_MODE)` → `AllowDarkModeForWindow(main, TRUE)` → `create_controls` (each child: `SetWindowTheme("DarkMode_Explorer")` IMMEDIATELY after its `CreateWindowExW`) → `ShowWindow`.
**Warning signs:** Visible flash on launch in screen-recording playback at ¼-speed; the "Screenshot 2026-05-23 190754.png" pattern (titlebar dark, menu/combobox still light) means the per-child SetWindowTheme step was skipped.

### Pitfall 2: Uxtheme Ordinal 135 Renamed Across Builds

**What goes wrong:** On Win10 1809 (build 17763), ordinal 135 exports `AllowDarkModeForApp(BOOL)` — a different signature. On 1903+ (build 18362+), it's `SetPreferredAppMode(PreferredAppMode)`. Calling the wrong signature corrupts the stack.
**Why it happens:** Microsoft repurposed the ordinal slot. The ordinal number is the same; the function it points to changed.
**How to avoid:** **Target 1903+ only.** Check `GetVersionExW` or RtlGetVersion for build ≥ 18362 before calling. On older builds, leave dark scrollbar/combobox unthemed (the Discretion fallback covers this case). The CONTEXT-locked fallback strategy already handles a null GetProcAddress; this pitfall extends the same defensive posture to the version check.
**Warning signs:** Crash on launch on Win10 1809 machines; otherwise silent corruption.

### Pitfall 3: DWMWA_USE_IMMERSIVE_DARK_MODE Value 19 vs 20 Across Builds

**What goes wrong:** `DwmSetWindowAttribute` returns `E_INVALIDARG` if you pass the wrong attribute number for the build.
**Why it happens:** Microsoft shipped the attribute as value 19 in Win10 1809 (17763), kept it as 19 through 1909 (18363), then **renumbered** to 20 in 20H1 (19041) when it was made public-documented.
**How to avoid:** Call BOTH — one will succeed, the other returns harmlessly. Existing `theme.rs::set_window_dark_mode` already does this correctly. **Do not "clean this up" into a single call.** Leave the dual-call pattern in place.
**Warning signs:** Titlebar stays light on a subset of Windows builds; the call returns `E_INVALIDARG` (0x80070057) but the code ignored the return.

### Pitfall 4: AddFontMemResourceEx Lifetime UB

**What goes wrong:** Crash on next garbage collection of the font slice, OR font glyphs render as squares.
**Why it happens:** Documentation says the font data must remain valid for the lifetime of the registration. Using a `Vec<u8>` that goes out of scope after `AddFontMemResourceEx` returns leaves GDI with a dangling pointer.
**How to avoid:** Use `include_bytes!` exclusively — that produces a `&'static [u8]` baked into the .exe's read-only data segment. Never copy into a heap allocation. The icon font lifetime is naturally process-long.
**Warning signs:** Font works in debug, breaks in release; or font breaks after an `Hfont` is destroyed and recreated.

### Pitfall 5: Bootstrap Icons WOFF2 vs TTF

**What goes wrong:** `AddFontMemResourceEx` returns NULL when fed a `.woff` or `.woff2`.
**Why it happens:** GDI's font loader only accepts TTF/OTF — WOFF is a web-only compression wrapper that requires a decoder.
**How to avoid:** Download from `https://github.com/twbs/icons/releases/tag/v1.11.3` — the release zip contains both `bootstrap-icons.css` (codepoint reference) AND `fonts/bootstrap-icons.ttf`. The npm package ships only `.woff2` — do NOT npm-install. Commit the renamed `.ttf` to `assets/`.
**Warning signs:** `num_fonts == 0` after `AddFontMemResourceEx`; tab labels render text but no glyph.

### Pitfall 6: Owner-Draw Menu Items Don't Get a Background Brush By Default

**What goes wrong:** Menu bar background stays the legacy 3D gray even when items are owner-drawn dark.
**Why it happens:** `MF_OWNERDRAW` only delegates the item rect — the menu's surrounding chrome (background between items, popup menu background) is still drawn by Windows using its system colors.
**How to avoid:** Call `SetMenuInfo(hmenu, &mi)` with `mi.fMask = MIM_BACKGROUND` and `mi.hbrBack = your_dark_brush`. Required on BOTH the top-level menu AND each popup menu (`GetSubMenu` then `SetMenuInfo` for each).
**Warning signs:** The vertical bar between menu items shows the legacy gray; the empty space at the bottom of a popup menu shows gray.

### Pitfall 7: WM_INITMENUPOPUP Fires for All Popups, Not Just the View Menu

**What goes wrong:** The CheckMenuItem calls fire for File / Help / context menus → either no-ops (best case) or unexpected re-checks (worst case).
**Why it happens:** `WM_INITMENUPOPUP` is broadcast for every popup menu about to display. The handler must filter.
**How to avoid:** Cache `state.view_menu: Hmenu` at menu construction time. In the handler: `if hmenu != state.view_menu { return DefWindowProc(...); }`.
**Warning signs:** Help-menu item appears checked when it shouldn't, or random clicks on File menu re-trigger settings save.

### Pitfall 8: Active Tab Persistence — `active_tab` Field Already Exists on DesktopState

**What goes wrong:** Duplicating the field, or shadowing the existing `usize` index with a `String`.
**Why it happens:** `src/desktop/state.rs` already declares `active_tab: usize` (default 1) — it powered the defunct 4-button toolbar's tab-like behavior. The new D-13 field is conceptually different (5-tab content tabs).
**How to avoid:** Repurpose the existing field. Two options the planner must pick:
- **Option A:** Keep `active_tab: usize` on `DesktopState`; convert to/from string at settings boundary. Wire format: `"details"|"top"|"extensions"|"duplicates"|"errors"` ↔ `0|1|2|3|4`. Pro: matches existing struct shape. Con: two conversions per save/load.
- **Option B:** Change `DesktopState.active_tab` to a `&'static str` or enum; settings field is a String directly. Pro: one representation throughout. Con: touches the existing toolbar hit-test code in `resize_controls` / `handle_mouse_click` (which is being deleted anyway in 02.1 — Option B is therefore cleaner).
**Recommendation:** **Option B** — the toolbar code that consumed `active_tab: usize` is being removed per D-06; replace the field with a typed enum `ActiveTab { Details, Top, Extensions, Duplicates, Errors }` in state.rs, serialize via `as_str()` / `from_str()` at the settings boundary.
**Warning signs:** Compile error "two fields named active_tab"; or settings file round-trips successfully but UI restores wrong tab.

### Pitfall 9: Palette Constant Divergence — Current theme.rs vs D-05 Spec

**What goes wrong:** Dark mode looks brown-tinted instead of neutral gray.
**Why it happens:** Current `palette_bg` in `src/desktop/theme.rs` returns `rgb(12,13,15)` (legacy values from Phase 1 module split). D-05 spec mandates `#1e1e1e` = `rgb(30,30,30)`. The values must be rewritten to match D-05.
**How to avoid:** During plan execution, REWRITE the palette constants in theme.rs to match UI-SPEC Color section exactly:
- `palette_bg` (dark) → `rgb(30, 30, 30)` (#1e1e1e)
- `palette_panel` (dark) → `rgb(45, 45, 45)` (#2d2d2d)
- `palette_text` (dark) → `rgb(204, 204, 204)` (#cccccc)
- `palette_line` (dark) → `rgb(58, 58, 58)` (#3a3a3a)
- `palette_disabled` (dark) → `rgb(122, 122, 122)` (#7a7a7a)
- Light mode: continue to delegate to `GetSysColor` per UI-SPEC table; hairline override = `rgb(229, 229, 229)` (#e5e5e5)
**Warning signs:** Side-by-side comparison with `images/Screenshot 2026-05-23 190754.png` shows colors don't match D-05.

### Pitfall 10: Bootstrap Icons Codepoints Are Version-Stable, But Not Externally Verified Here

**What goes wrong:** Tab strip renders empty boxes or wrong glyphs.
**Why it happens:** This research could not externally verify the v1.11.3 codepoints (web search did not return authoritative hex values). The UI-SPEC table values (`\u{F4A6}`, `\u{F1C6}`, `\u{F3CB}`, `\u{F759}`, `\u{F33A}`, `\u{F26E}`) are planner-recommended picks derived from the Bootstrap Icons community catalog.
**How to avoid:** Executor MUST verify each codepoint against the actual bundled `.ttf` glyph table OR the official `bootstrap-icons.css` shipped in the same v1.11.3 release zip (search the .css for each `bi-name` and confirm the `\f...` content rule matches). Bootstrap Icons codepoints have been stable since v1.4.1 but per-icon verification is cheap insurance.
**Warning signs:** Tab strip glyphs visibly wrong (e.g. a folder where a bar chart should be); empty Tofu square `□` glyph means the codepoint isn't mapped in this font version.

### Tab Strip Hit-Test in WM_LBUTTONDOWN

```rust
// In src/desktop/tabs.rs (NEW)
WM_LBUTTONDOWN => {
    let x = LOWORD(lparam as u32) as i32;
    // Compute tab rects (cached on DesktopState.tab_rects, recomputed in WM_SIZE)
    let clicked = with_state_mut(|state| {
        state.tab_rects.iter().enumerate()
            .find(|(_, rc)| x >= rc.left && x < rc.right)
            .map(|(i, _)| i)
    });
    if let Some(Some(index)) = clicked {
        PostMessageW(GetParent(hwnd), WM_COMMAND,
            MAKEWPARAM(ID_TAB_DETAILS + index as u16, 0), hwnd as Lparam);
    }
    return 0;
}
// Parent WM_COMMAND arm: with_state_mut → state.active_tab = ActiveTab::from_idx(index)
//                       → ShowWindow swap → InvalidateRect tab strip
```

## Open Questions

1. **Submenu structure for Appearance.** CONTEXT D-06 hints at a "View → Appearance → ● Light / ● Dark" radio-item submenu; UI-SPEC recommends a flat checkable "Dark Mode" item. Plan must pick one.
   - What we know: D-06 names both forms ambiguously; UI-SPEC explicitly recommends flat for simplicity.
   - What's unclear: Future-proofing — if "Auto" mode is ever added (deferred per Deferred Ideas), the radio-group form fits more naturally.
   - **Recommendation:** Ship flat for 02.1. If "Auto" lands later, refactor to a radio-item submenu then.

2. **`ActiveTab` enum vs `&'static str` discriminant.** Pitfall 8 Option B recommends an enum; Rust's borrowck makes a `&'static str` discriminant slightly cleaner for `match` arms in some patterns.
   - What we know: Both work; enum is more idiomatic Rust.
   - What's unclear: Whether the tab-strip code wants to iterate tab names (favors a `[&'static str; 5]` constant array alongside the enum).
   - **Recommendation:** Enum + a const array `pub const TAB_NAMES: [&str; 5] = ["details", "top", "extensions", "duplicates", "errors"];` for serialization + iteration. Index of enum variant = index in array.

3. **Popup-menu checkmark glyph choice.** UI-SPEC declares `\u{F26E}` (`bi-check`) drawn via the icon font, with fallback to `√` (U+221A) if the icon font fails to load.
   - What we know: Both work; bi-check matches the rest of the icon family.
   - What's unclear: Whether the icon-font-not-loaded path is actually reachable (process-lifetime registration + static asset means it should never fail in production).
   - **Recommendation:** Use bi-check unconditionally; if `register_icon_font` returns NULL, the entire phase fails earlier (tab strip glyphs are also broken) — the menu checkmark is not a useful fallback path.

4. **Tab-strip hover state.** UI-SPEC explicitly says no visual hover feedback (Apple-HIG restraint), but allows cursor change to `IDC_HAND` on hover.
   - What we know: Pixel state stays still; cursor MAY change.
   - **Recommendation:** Set `IDC_HAND` on hover in `WM_SETCURSOR`. No visual repaint.

5. **Drive-letter parsing in D-11.** UI-SPEC says "first char if alphabetic, else `'C'`" — but what if `settings.last_path` starts with `\\?\C:\...` (UNC long-path prefix) or `\\server\share\...`?
   - What we know: Most personal-use paths are `C:\` form.
   - **Recommendation:** Strip a leading `\\?\` prefix if present, then take the first alphabetic char before `:`; if no match, fall back to `'C'`. UNC paths (`\\server\...`) have no drive letter — fall back to `'C'`.
