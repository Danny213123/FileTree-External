## Shared Patterns

### Save-on-mutate (THE locked persistence idiom)

**Source:** `src/desktop/state.rs:137-188` (definition) + `src/desktop/mod.rs:346-360` (call site).
**Apply to:** every 02.1 file/code path that mutates `state.settings.*` — specifically the new ID_VIEW_SHOW_HIDDEN / ID_VIEW_SHOW_FILES / ID_VIEW_DARK_MODE / ID_TAB_DETAILS..ERRORS WM_COMMAND arms.

```rust
// Canonical sequence (state.rs + mod.rs:346-360):
let snap = with_state_mut(|state| {
    state.settings.<field> = <new value>;        // 1. mutate
    state::snapshot_for_save(state)              // 2. snapshot inside lock
}).flatten();
if let Some(snap) = snap {                       // 3. release lock implicitly (closure exit)
    state::save_settings_if_dirty(snap);         // 4. save OUTSIDE the lock
}
```

**Why this exact shape:** `SettingsStore::save` does a synchronous atomic file write that involves OS calls; holding `STATE.lock()` across those calls would deadlock any reentrant Win32 message dispatch (per the `with_state_mut`/`try_lock` discipline at state.rs:190-201). Discrete events (tab switch, checkbox toggle, drive change) save immediately; drag events use the `pending_persist` flag instead.

### Reentrancy-safe state access

**Source:** `src/desktop/state.rs:190-201` (`with_state_mut` uses `try_lock` not `lock`).
**Apply to:** every callback that runs inside the Win32 message pump — including the new `WM_INITMENUPOPUP`, `WM_DWMCOLORIZATIONCOLORCHANGED`, `WM_DRAWITEM`, `WM_MEASUREITEM`, `WM_DPICHANGED` arms.

```rust
// src/desktop/state.rs:190-201 — DO NOT replace try_lock with lock; Win32 sends
// synchronous messages back into the window proc during SetWindowTextW / EnableWindow
// / SendMessageW, which would deadlock std::Mutex (not reentrant).
let mut state = state.try_lock().ok()?;
Some(callback(&mut state))
```
