- `src/desktop/theme.rs:51` `uxtheme_ordinals()` — `OnceLock<UxthemeOrdinals>` resolver that calls `LoadLibraryW("uxtheme.dll")` once, then `GetProcAddress` at ordinals 135 (SetPreferredAppMode) / 133 (AllowDarkModeForWindow) / 136 (FlushMenuThemes). Each pointer is independently null-checked; non-null pointers are `mem::transmute`d into typed `extern "system"` fn pointers stored as `Option<fn>`. On Win10 1809 (T-02.1-03-01) the ordinal-135 signature mismatch is mitigated by leaving `set_preferred_app_mode = None`, so the caller silently degrades (scrollbar/combobox stay light) but never crashes.
- `src/desktop/theme.rs:119` `selected_text_for_accent(r, g, b) -> Dword` — simple linear WCAG luminance (`0.2126*r + 0.7152*g + 0.0722*b`, byte-normalized); returns `rgb(0,0,0)` when luminance > 0.6, else `rgb(255,255,255)`.
- `src/desktop/theme.rs:140` `refresh_accent(state: &mut DesktopState)` — calls `DwmGetColorizationColor` (out-param ARGB Dword), strips the alpha byte, byte-swaps ARGB→BGR for `COLORREF`, writes `state.accent_color` and recomputes `state.selected_text_color` via `selected_text_for_accent`. On non-zero HRESULT the function returns early leaving both fields untouched (so the cached value is monotonically "best we've seen so far").
- `src/desktop/theme.rs:165` `apply_dark_mode_to_window(hwnd, enabled)` — `unsafe` helper that (1) calls the existing `set_window_dark_mode` preserving the load-bearing dual `DwmSetWindowAttribute(20, ...)` / `(19, ...)` cross-version pattern (Pitfall 3), (2) calls `AllowDarkModeForWindow` if the uxtheme ordinal-133 pointer resolved non-null, (3) calls `SetWindowTheme(hwnd, "DarkMode_Explorer", null)` to flip the visual style.
- `src/desktop/state.rs:63` `pub(super) accent_color: Dword` and `:67 pub(super) selected_text_color: Dword`; both initialized to `0` in `DesktopState::new` (line 132–133). A `0` accent before the first `refresh_accent` call paints as black — visually degraded but not a crash (matches doc-comment).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] VALIDATION luminance test boundary inputs recomputed for the locked formula**

- **Found during:** Task 2 RED → GREEN
- **Issue:** The plan's `<behavior>` block listed two test boundary inputs — `(180, 200, 220)` "lum ≈ 0.5919 → white text" and `(190, 210, 220)` "lum ≈ 0.6437 → black text". Those luminance numbers are correct only under WCAG gamma-corrected luminance. The plan's `<action>` block (which is the locked implementation contract) specifies the SIMPLE linear formula `0.2126*R + 0.7152*G + 0.0722*B`. Under the simple formula, `(180, 200, 220)` evaluates to ≈ 0.773 (above threshold) — so the test would receive black text, not white, and fail.
- **Fix:** Kept the locked simple formula (it matches the action block AND the `selected_text_for_accent` interface contract). Replaced the boundary inputs in `accent_luminance` / `selected_text_threshold` with mathematically-correct values for the simple formula:
  - `(150, 150, 150)` → lum ≈ 0.588 (below 0.6 → returns white text)
  - `(155, 155, 155)` → lum ≈ 0.608 (above 0.6 → returns black text)
  Added an inline test comment explaining that boundary cases were computed against the simple linear luminance formula adopted in `selected_text_for_accent`.
- **Files modified:** `src/desktop/theme.rs` (test module only — production formula unchanged)
- **Commit:** `0b02375` (the GREEN commit; the RED commit `aa17d86` already used the corrected inputs because RED was authored after the inconsistency was detected)
