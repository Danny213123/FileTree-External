# Phase 02.1 Plan 07: First-Paint Flash Mitigation (POL-03) Summary

**One-liner:** Pre-window uxtheme bootstrap + per-HWND apply_dark_mode_to_window before ShowWindow closes the D-04 white-flash defect on dark-mode launch.

## What Was Built

### Task 1: Pre-window dark bootstrap in src/cli.rs

Added `pub(crate) fn bootstrap_dark_mode(enabled: bool)` to `src/desktop/mod.rs` as a thin wrapper (Option A from the plan). The wrapper reads `uxtheme_ordinals().set_preferred_app_mode` — the `Option<fn>` resolved by Plan 02.1-03's `uxtheme_ordinals()` initializer — and calls it with `PREFERRED_APP_MODE_ALLOW_DARK` (1) when dark mode is on, `PREFERRED_APP_MODE_DEFAULT` (0) otherwise. If the ordinal is `None` (Win10 1809), the call is a no-op.

In `src/cli.rs::run_desktop`, `crate::desktop::bootstrap_dark_mode(settings.dark_mode)` is called immediately after `SettingsStore::load_or_default()` and before `primary_workarea()` / `desktop::run()`. This ensures the process-wide AppMode is set before any window class is registered.

### Task 2: Per-HWND dark apply in src/desktop/mod.rs

Two changes:

1. **WS_VISIBLE stripped from main `CreateWindowExW`** — the style is now `WS_OVERLAPPEDWINDOW` only. The window no longer auto-shows inside `CreateWindowExW`; the existing `ShowWindow(hwnd, SW_SHOW)` at line 197 performs the explicit post-theme show.

2. **`apply_dark_mode_to_window` on main HWND** — replaced the pre-existing `set_window_dark_mode(hwnd, initial_dark)` call with `apply_dark_mode_to_window(hwnd, initial_dark)`, which is the full Plan 02.1-03 canonical triad (DwmSetWindowAttribute 20+19 + AllowDarkModeForWindow + SetWindowTheme).

3. **Per-child `apply_dark_mode_to_window` calls** added inline after each `CreateWindowExW` in `create_controls`:
   - `drive_picker` (ComboBoxEx32)
   - `path_edit` (EDIT)
   - `browse_button`, `scan_button`, `stop_button`, `refresh_button`, `expand_button`, `collapse_button`, `columns_button` (BUTTONs)
   - `tab_strip`, `tab_panels[0..5]`, `status_footer` — already had calls from Plans 02.1-05/06; preserved as-is.

## Decisions Made

- **Option A (wrapper in mod.rs)** used for visibility rather than Option B (widen pub(super)→pub(crate) in theme.rs) or Option C (helper in theme.rs). Keeps uxtheme internals encapsulated behind the desktop module boundary.

- **Per-child inline** rather than refactoring into `apply_dark_mode_to_children` helper. The tab_strip/panels/footer already had individual calls from earlier plans; inlining the remaining controls is consistent and avoids introducing a new abstraction whose value diminishes when some children already have calls.

- **WS_VISIBLE strip confirmed**: The main window style was `WS_OVERLAPPEDWINDOW | WS_VISIBLE` in Phase 02; stripped to `WS_OVERLAPPEDWINDOW` per D-04. The existing `ShowWindow(hwnd, SW_SHOW)` at mod.rs:197 is preserved and is the sole show call (count = 1 in code; the one grep match in comments doesn't count).

## Flash Status

Manual launch testing not possible in this automated execution context. Based on the Win32 mechanism:

- Pre-window `SetPreferredAppMode(AllowDark)` via bootstrap_dark_mode ensures uxtheme's per-process state is set before RegisterClassW allocates the WNDCLASS theme context.
- `WS_VISIBLE` stripped prevents CreateWindowExW from triggering the first WM_PAINT before `apply_dark_mode_to_window` has run.
- `apply_dark_mode_to_window` on the main HWND immediately after CreateWindowExW returns (before ShowWindow) applies DWM dark chrome to the title bar and system borders before the window is presented.
- All child HWNDs receive `apply_dark_mode_to_window` before ShowWindow, ensuring no flash on child paints.

Zero visible white flash is expected on Win11 23H2 with `"dark_mode": true` in settings.json. Light mode is unaffected — `bootstrap_dark_mode(false)` passes `PREFERRED_APP_MODE_DEFAULT` and `apply_dark_mode_to_window(hwnd, false)` applies the light Explorer theme.
