<objective>
Close D-04 (first-paint flash) and D-10 (system theme honored on first launch) by:

1. **Pre-window dark bootstrap in src/cli.rs::run_desktop:** Load settings via SettingsStore. If `settings.dark_mode == true`, call `uxtheme_ordinals().set_preferred_app_mode(PREFERRED_APP_MODE_ALLOW_DARK)` BEFORE `desktop::run` is invoked. This tells uxtheme to dark-theme any window class subsequently registered + any built-in scrollbar/combobox theming that gets resolved on window creation.

2. **Per-HWND dark application in src/desktop/mod.rs::run:** Immediately after `CreateWindowExW` returns the main HWND, call `theme::apply_dark_mode_to_window(hwnd, settings.dark_mode)` (the Plan 02.1-03 consolidated helper — does DwmSetWindowAttribute 20+19 + AllowDarkModeForWindow + SetWindowTheme). This happens BEFORE the first `ShowWindow(hwnd, SW_SHOW)`. Same for every child HWND in `create_controls` — path_edit, drive_picker, scan_button (if any survives toolbar deletion), tab_strip, tab_panels[5], status_footer.

Purpose: Without this plan, even with correct palette + correct dark-themed children, the moment of first paint shows the OS default (light) chrome for ~50-200 ms before the existing `apply_theme` call re-themes the window. Per RESEARCH Pattern 5 + Pitfall 3, the fix is twofold: (a) set process-wide AppMode before the first window class is registered, and (b) apply the per-HWND DWM attribute BEFORE the first ShowWindow.

This plan is intentionally small (Wave 3) because it depends on:
- Plan 02.1-03's `apply_dark_mode_to_window` helper and `uxtheme_ordinals()` resolver.
- Plan 02.1-05's tab_strip + tab_panels HWNDs (must exist to be themed).
- Plan 02.1-06's status_footer HWND (must exist to be themed).

Output:
- `src/cli.rs`: ~6 lines added to `run_desktop` between settings load and `desktop::run` invocation.
- `src/desktop/mod.rs`: 1 line added after the main `CreateWindowExW` in `run`, plus ~8 lines added in `create_controls` (one per child HWND) for the per-child apply.

No new fields, no new helpers, no tests (this is integration wiring; behavior is validated by manual launch).
</objective>

The `apply_theme(state)` call from Phase 02 (theme.rs:48-86) already covers per-child theming AFTER the window is up. The DIFFERENCE in Plan 02.1-07 is doing it BEFORE the window is shown — pre-show theme prevents the white-flash. apply_dark_mode_to_window (Plan 02.1-03) is the per-HWND helper; this plan just sequences when it's called.

Note on cross-version SetPreferredAppMode behavior (Pitfall 2 from Plan 02.1-03):
- On Win10 1809: ordinal 135 was `AllowDarkModeForApp(BOOL)` with different semantics. Calling it with arg = 1 (PREFERRED_APP_MODE_ALLOW_DARK) accidentally works (BOOL TRUE = 1).
- On Win10 1903+ / Win11: ordinal 135 is `SetPreferredAppMode(PreferredAppMode)`. Calling with 1 = AllowDark.
- The semantic accident means our single call works on all supported builds. No version-gating needed.
