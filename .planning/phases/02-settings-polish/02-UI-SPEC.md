# Phase 2 — UI Design Contract

> Visual and interaction contract for the FileTree Win32 native desktop. This phase introduces three new surfaces (path bar, status bar, accelerator-table shortcut model) and one invisible surface that has visible side effects (settings persistence). Generated by gsd-ui-researcher; verified by gsd-ui-checker.
>
> **Framing:** FileTree is a raw Win32 GDI-painted desktop application — there is no design system, no component library, no CSS. The "tokens" below are concrete logical-pixel values fed into `CreateWindowExW`, `MoveWindow`, `SetWindowTextW`, GDI fills, and DPI scaling. All measurements are expressed in **logical pixels at 96 DPI** and MUST be scaled at runtime via `GetDpiForWindow(hwnd) * value / 96` before being passed to Win32 APIs. The existing app does not yet honor DPI; introducing the helper here pays forward to Phase 8 visualizations.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (raw Win32 GDI) |
| Preset | not applicable |
| Component library | Win32 Common Controls v6 (`ComboBoxEx32`, `msctls_statusbar32`, `BUTTON`, `EDIT`) — already linked via Comctl32.dll v6 with the visual-styles manifest enabled in `desktop/mod.rs::enable_visual_styles`. New surfaces MUST request both `ICC_USEREX_CLASSES` (for ComboBoxEx32) and `ICC_BAR_CLASSES` (for msctls_statusbar32) when `InitCommonControlsEx` runs at startup. |
| Icon library | Native shell icons via `SHGetFileInfoW` — already in use for the tree. No new icon system introduced this phase (drive-picker icons explicitly deferred per RESEARCH Open Question #3). |
| Font | **Segoe UI 9pt** for all new surfaces (path bar edit, drive picker, status bar). Acquired via `CreateFontIndirectW` with `lfFaceName = "Segoe UI"`, `lfHeight = -MulDiv(9, GetDeviceCaps(hdc, LOGPIXELSY), 72)`. The existing `DesktopState.font` (already created in `desktop/state.rs` at app startup) is reused — do NOT create a second font handle. Rationale: matches Windows 10/11 system UI default; the existing toolbar already uses this font handle. |

### Dark mode coherence

The new surfaces MUST honor the existing `DARK_MODE_ATOMIC: AtomicBool` flag and the `palette_*(state)` helpers in `src/desktop/theme.rs`. No new palette entries are introduced this phase — every new pixel reuses an existing palette function. Common controls (ComboBoxEx, msctls_statusbar32) DO NOT honor dark mode through normal channels; they MUST be initialized with `SetWindowTheme(hwnd, L"DarkMode_Explorer", NULL)` immediately after `CreateWindowExW` when `state.dark_mode == true`, and re-themed with `L"Explorer"` when the user toggles light mode. This pattern is already established for `state.path_edit` and `state.status` in `theme.rs::apply_theme` — extend the existing list, do not invent a parallel path.

### Visual identity coherence with the embedded web UI

The web UI in `web/styles.css` uses Indigo-500 (`#6366f1`) as the accent. The desktop already mirrors this via `palette_percent_fill(state)` returning `rgb(92, 93, 242)` in dark mode and `rgb(65, 122, 232)` in light mode (an Indigo-ish blue tuned for Win32 GDI rendering). Phase 2 introduces no new accent values — the focus ring on the path edit, the active-pane highlight on the status bar, and the keyboard-shortcut hover state all draw from the existing `palette_percent_fill` / `palette_selected` functions. **No new color tokens.**

## Component Inventory & Layout Tokens

This section is the planner's and executor's primary lookup. Every measurement is locked.

### Path bar (top of main window) — POL-01

| Token | Value | Notes |
|-------|-------|-------|
| Bar height | 32 logical px | `CreateWindowExW` height passed to the path-bar container row in `desktop/paint.rs::resize_controls`. |
| Bar horizontal inset | 8 logical px | Left and right margin from window client edge. |
| Bar vertical position | Directly below tab strip (`table_top() - 36`) | Slots in above the existing ribbon body; see `paint.rs::draw_toolbar_background` for the existing 30px tab strip + ribbon body the path bar lives over. |
| Drive picker width | **80 logical px** | Fixed width; sufficient for `"X: Local Disk"` truncated to `"X: Local…"` via `ComboBoxEx32`'s built-in ellipsis. |
| Gap between picker and edit | 4 logical px (xs) | Visual breathing room. |
| Path edit width | `bar_width - 80 - 8 - 8 - 4` | i.e. fills remaining horizontal space after picker + insets + gap. Computed on every WM_SIZE. |
| Focus ring | Win32 default (themed) | Do NOT custom-paint a focus ring. `SetWindowTheme(edit, L"DarkMode_Explorer", NULL)` gives the user the Windows-blessed focus indicator (a 1px indigo outline on Win11), which already matches our accent. |
| Autocomplete dropdown | OS-painted via `SHAutoComplete(SHACF_FILESYS_DIRS \| SHACF_AUTOSUGGEST_FORCE_ON \| SHACF_AUTOAPPEND_FORCE_ON)` | No styling control — Explorer-native dropdown appearance. This is the correct trade per RESEARCH Pattern 5. |

**Drive picker entry format (POL-01):** `"X: Label"` where `X` is the drive letter and `Label` is `GetVolumeInformationW`'s volume label (capped to 16 chars; if empty, fall back to drive-type name per `GetDriveTypeW`):

| `GetDriveTypeW` result | Fallback label |
|------------------------|----------------|
| DRIVE_FIXED (3) | `Local Disk` |
| DRIVE_REMOVABLE (2) | `Removable` |
| DRIVE_CDROM (5) | `CD/DVD` |
| DRIVE_REMOTE (4) | `Network` |
| DRIVE_RAMDISK (6) | `RAM Disk` |
| DRIVE_UNKNOWN (0) / DRIVE_NO_ROOT_DIR (1) | **excluded from picker** |

**Network drives (DRIVE_REMOTE):** **INCLUDED** in the picker. Personal-use single-developer app — author may have mapped network shares (the existing scan engine already handles them). Skipping them would silently lose functionality.

**Drive icons in picker:** **DEFERRED to a follow-up polish task** (per RESEARCH Open Question #3 recommendation). Phase 2 picker is text-only. Adding `SHGFI_SYSICONINDEX` + an `HIMAGELIST` is a separate concern that can land any time after Phase 2 without changing this contract.

### Status bar (bottom of main window) — POL-03

Five panes, fixed left-to-right order. Pane right-edges computed on WM_SIZE via the formula below.

| Pane Index | Label | Logical Width | Right-Edge Formula |
|-----------|-------|---------------|---------------------|
| 0 PANE_FILES | files count | 180 logical px | `dpi_scale(180)` |
| 1 PANE_FOLDERS | folders count | 180 logical px | `dpi_scale(360)` |
| 2 PANE_ERRORS | errors count | 140 logical px | `dpi_scale(500)` |
| 3 PANE_ELAPSED | elapsed time | 140 logical px | `dpi_scale(640)` |
| 4 PANE_THROUGHPUT | throughput MB/s | fills remaining | `-1` (passed to `SB_SETPARTS` for "fills to end") |

**Layout formula** (lives in `desktop/paint.rs`, called from `resize_controls` on WM_SIZE):

```text
fn compute_status_parts(client_width: i32, dpi: u32) -> [i32; 5] {
    let scale = |v: i32| (v * dpi as i32) / 96;
    let p0 = scale(180);
    let p1 = p0 + scale(180);
    let p2 = p1 + scale(140);
    let p3 = p2 + scale(140);
    let p4 = -1;  // last pane fills to client_width
    [p0, p1, p2, p3, p4]
}
```

**Pane text alignment:** All five panes are **left-aligned** with 8px inset from the pane's left edge. Status bar text is not a place for numeric right-alignment — five right-aligned panes adjacent would visually merge. Numbers stay readable when left-aligned because they share a common prefix label.

**Pane text format:**

| Pane | Format (active scan) | Format (idle / pre-scan) | Format (completed scan) |
|------|----------------------|--------------------------|--------------------------|
| files | `"1,234 files"` (thousands-separator, lowercase noun) | `"-- files"` | `"1,234 files"` (frozen at completion) |
| folders | `"567 folders"` | `"-- folders"` | `"567 folders"` |
| errors | `"8 errors"` | `"-- errors"` | `"8 errors"` |
| elapsed | `"0:42"` (M:SS for < 1 hour) or `"1:23:45"` (H:MM:SS for >= 1 hour) | `"--:--"` | (frozen at completion) |
| throughput | `"12.4 MB/s"` (1 decimal, single space before unit) | `"-- MB/s"` | **`"-- MB/s"`** (per CONTEXT "specific ideas" — never show stale throughput) |

**Idle marker:** ASCII double-hyphen `--`. Specifically NOT an en-dash `–` — the status bar uses `SetWindowTextW` (Unicode) but the visual weight of ASCII `--` reads more clearly at 9pt Segoe UI on a 24px-tall pane than an en-dash, which can look like a hairline at the same size.

**Update cadence:** Driven by the existing 1500 ms `WM_SCAN_PROGRESS` post from `src/scan.rs` (no new timer per CONTEXT Claude's-discretion). On each tick, the four count/elapsed panes are recomputed and rewritten via `SendMessageW(status, SB_SETTEXTW, pane_index, text_ptr)`. The throughput pane is recomputed as `bytes_so_far / elapsed_secs` and formatted via `format_throughput(bytes, ms)`. On scan completion, the throughput pane immediately switches to `"-- MB/s"`; the count panes freeze at their final values. On a new scan start, all five panes initialize to the active-scan format with zeros (`"0 files"`, `"0:00"`, `"0.0 MB/s"`).

### Keyboard shortcut focus / conflict model — POL-02

Six accelerators registered via `CreateAcceleratorTableW` and dispatched in the message pump via `TranslateAcceleratorW` (which runs BEFORE `TranslateMessage` / `DispatchMessageW`, so the accelerator wins over edit-control default key handling — per RESEARCH Pitfall #8).

| Shortcut | Command ID | Focus Model | Behavior in Edit Controls | Behavior During Scan |
|----------|-----------|-------------|---------------------------|----------------------|
| Enter | `CMD_SCAN` (0xA001) | **Always fires.** Path edit's existing Enter-to-scan binding is removed and replaced by the accelerator-routed `CMD_SCAN` — single dispatch path. | Wins over edit-control beep (single-line edit beeps on Enter by default). | If scan in flight, `CMD_SCAN` handler no-ops (button is already disabled via `EnableWindow(scan_button, false)`). |
| Esc | `CMD_CANCEL_SCAN` (0xA002) | **Conditional.** Fires only when `state.scanning == true`. Otherwise, the accelerator handler falls through (returns 0 from `TranslateAcceleratorW`'s WM_COMMAND), allowing the edit's default Esc behavior (revert / close dropdown) to run. | When path edit has focus AND scan in flight: Esc cancels scan, does NOT revert edit text. | Primary trigger for cancel. |
| Del | `CMD_DELETE_SEL` (0xA003) | **Focus-conditional.** Fires ONLY when the custom tree list has focus (i.e., `GetFocus() == state.list`). When path edit has focus, Del passes through to the edit (which deletes the next character — standard EDIT behavior). | Suppressed in edit controls — accelerator handler checks `GetFocus()` and no-ops if it's not the list HWND. | Phase 2 stub: handler logs and no-ops (Phase 5 wires the IFileOperation pipeline). |
| Ctrl+F | `CMD_FOCUS_SEARCH` (0xA004) | **Always fires.** No conflict in Phase 2 (no search control exists yet). | Wins over edit's default (which has no Ctrl+F binding). | No-op stub in Phase 2; Phase 3 wires the search-focus call. |
| Ctrl+E | `CMD_EXPORT` (0xA005) | **Always fires.** | Wins over edit's default. | Runs even during scan — export operates on whatever data is already loaded (existing behavior). |
| F5 | `CMD_REFRESH` (0xA006) | **Always fires.** | No edit-control conflict (F5 is not a standard edit binding). | **Restarts the scan.** If scan in flight, the handler first sets the cancel atomic and waits one message-pump iteration (to let `current_cancel` fire), then starts a fresh scan from the current path edit contents. Decision: per additional_context, "always restart" is cheaper than queueing and matches user expectation that F5 = "do it again now." |

**Cross-cutting rule:** All six accelerator-handler `WM_COMMAND` arms in `desktop/state.rs::window_proc` MUST be no-throw, no-block — they post intent (set an atomic, enqueue a Wave, call `EnableWindow`) and return. The actual work runs on the existing background scan thread or in the next paint cycle. This preserves the constraint that "the scan UI must remain responsive while workers are scanning."

### Settings persistence visible behaviors (SET-01..05)

Settings persistence is invisible (a JSON file on disk) but has three visible behaviors that this contract pins:

1. **Window restore order — no jank.** On launch, `cli::run` MUST: (a) read `settings.json` into a `Settings` struct, (b) extract persisted `window.x / window.y / window.w / window.h`, (c) pass those values directly to `CreateWindowExW` (NOT `CW_USEDEFAULT`), (d) then `ShowWindow(hwnd, SW_SHOW)`. **NEVER** create at defaults and call `SetWindowPos` after — that produces a one-frame flash in the default position that users perceive as broken. If the persisted geometry would place the window off-screen (the user disconnected a monitor between sessions), clamp to the primary monitor's work area via `SystemParametersInfoW(SPI_GETWORKAREA, ...)` BEFORE passing to `CreateWindowExW` — clamping in advance preserves the no-jank invariant.

2. **Atomic-write failure UX.** Per CONTEXT D-03: silent in release builds, `eprintln!` in debug builds. **NEVER** show a `MessageBoxW` for a settings save failure — that is a settings-of-the-polish overreaction that breaks the user's flow. The status bar does NOT acquire a "settings save failed" indicator this phase (deferred YAGNI).

3. **Single-instance focus-pop UX.** Per CONTEXT D-04 + RESEARCH Pitfall #9: second instance calls `AllowSetForegroundWindow(primary_pid)` before sending WM_COPYDATA; primary's WM_COPYDATA handler calls `SetForegroundWindow(hwnd)` itself. **No custom flash animation** — Windows's default behavior (taskbar icon flashes if foreground steal is denied; window pops to front if granted) is the correct, OS-blessed UX. Adding a custom flash would compete with the OS's existing affordance.

## Typography

Single font handle (`DesktopState.font` and `DesktopState.bold_font`, already created at startup) is reused across all surfaces. No new typography roles introduced — this phase reuses two existing roles only.

| Role | Size | Weight | Line Height | Used For (Phase 2 surfaces) |
|------|------|--------|-------------|-----------------------------|
| Body | 9pt Segoe UI (= 12 logical px at 96 DPI) | Regular (FW_NORMAL = 400) | Single-line (handled by `DT_SINGLELINE \| DT_VCENTER` in `DrawTextW`) | Path edit text, drive picker entries, status bar pane text |
| Label | 9pt Segoe UI | Semibold (FW_SEMIBOLD = 600) | Single-line | (Not introduced this phase — preserved for future status-bar label prefixes if added) |

Rationale for two roles (not 3-4): the Phase 2 surfaces are utility chrome (a path input, drive list, and 5 status panes). They consume body weight only; introducing a heading weight would draw attention to chrome that should sit in the user's peripheral vision while they scan a directory tree. The "must declare 3-4 sizes" guideline in the gsd-ui-researcher template is calibrated for content-driven web UIs; for a native Win32 utility window with no document body, two reused roles is correct.

**No font instantiation in Phase 2.** All text uses the existing `DesktopState.font` handle via `SelectObject(hdc, state.font as Hgdobj)`. No new `CreateFontIndirectW` calls.

## Color

The desktop already has a complete dark/light palette in `src/desktop/theme.rs::palette_*` functions. Phase 2 reuses these functions exclusively — **no new palette entries are introduced.** The 60/30/10 split below maps the existing palette onto the standard model so the design checker can validate.

| Role | Dark mode | Light mode | Source | Usage in Phase 2 |
|------|-----------|------------|--------|------------------|
| Dominant (60%) | `rgb(12, 13, 15)` near-black | `rgb(242, 244, 247)` near-white | `palette_bg(state)` | Main window background; status bar background (overridden via `SetWindowTheme("DarkMode_Explorer")` to take the OS dark variant). |
| Secondary (30%) | `rgb(28, 30, 34)` panel grey | `rgb(236, 238, 241)` panel grey | `palette_panel(state)` | Path bar background, status bar visual base (after theme inheritance). |
| Accent (10%) | `rgb(92, 93, 242)` indigo | `rgb(65, 122, 232)` blue | `palette_percent_fill(state)` | **Reserved for:** (a) the path edit focus ring (themed-default rendering, but its color is exactly this hex on Win11), (b) the active-pane highlight if/when the status bar grows a clickable pane in a later phase (NOT used in Phase 2), (c) carried forward from existing tree-row `palette_selected`. |
| Destructive | (none introduced this phase) | (none introduced this phase) | — | No destructive actions surface in Phase 2 UI (Del shortcut stub doesn't show any UI; the actual delete-with-red-confirmation lands in Phase 5). |
| Muted text | `rgb(156, 165, 174)` | `rgb(91, 100, 112)` | `palette_muted(state)` | Status bar "--" idle markers; status bar pane text when the count is zero (e.g., `"0 errors"` is muted; `"8 errors"` is full-text color to draw attention). |
| Full text | `rgb(240, 244, 248)` | `rgb(18, 22, 27)` | `palette_text(state)` | Status bar pane text for non-zero counts; path edit text content; drive picker entries. |

**Accent reserved for (explicit list — never "all interactive elements"):**

1. Path edit focus ring (rendered by Win32 themed default after `SetWindowTheme(L"DarkMode_Explorer")` — the color happens to match `palette_percent_fill`).
2. Tree-row selected-background state (existing, unchanged this phase — listed for completeness so the checker can verify accent is not over-deployed).

That's it. Two surfaces. The path bar text caret uses the OS-default caret color (white on dark / black on light), NOT the accent — Win32 caret color is system-wide and we don't override it.

**Errors-pane color rule (POL-03 spec extension):** When the active scan's error count > 0, the errors pane text MUST use `palette_text(state)` (full-weight). When it equals zero (active or idle), it MUST use `palette_muted(state)`. Rationale: errors > 0 is the one piece of status-bar info that warrants attention; counts of zero should fade. This is the closest Phase 2 gets to a semantic color — and intentionally avoids introducing red, because:
- Red would shout for attention on every error, including benign ones (a single "access denied" on `C:\System Volume Information` during a `C:\` scan is normal).
- The existing Errors **tab** already gets full attention via its tab badge; the status pane is a peripheral counter.

**Voice rules:**
- All counts use lowercase nouns (`files`, `folders`, `errors`) — these are field labels, not titles.
- Thousands-separator comma (`1,234` not `1234` not `1.234`) for US-English locale — matches the existing `format_count_ui` helper in `paint.rs`.
- All status-bar strings are **sentence fragments, not sentences** — no trailing periods. They live in a peripheral data pane, not a narrative.
- No emoji. No Unicode arrows. ASCII-clean except for the OS-native font glyphs.

## Interaction States

### Path bar — drive picker

| State | Visual | Behavior |
|-------|--------|----------|
| Default | Themed combobox, dropdown collapsed, shows current drive letter + label | Click or Alt+Down opens dropdown. Tab moves focus to path edit. |
| Open | Dropdown listbox showing all enumerated drives (excluding `DRIVE_UNKNOWN` / `DRIVE_NO_ROOT_DIR`) | Arrow keys navigate; Enter selects; Esc closes without changing. |

| Disabled (during scan) | Themed disabled appearance (greyed) | `EnableWindow(picker, false)` during scan; re-enabled on scan completion or cancel. Rationale: changing the drive mid-scan is incoherent. |

### Path bar — path edit

| State | Visual | Behavior |
|-------|--------|----------|
| Default | Themed EDIT control, current path text, no focus ring | Click or Tab focuses. |

## Layout Reflow Behavior (WM_SIZE)

`desktop/paint.rs::resize_controls` is the existing layout-reflow hot path. Phase 2 extends it but does NOT introduce a parallel layout engine.

**Order of operations on WM_SIZE:**

1. Read `client_width` and `client_height` from `GetClientRect`.
2. Read `dpi = GetDpiForWindow(state.hwnd)` (Win10 1607+ API — fallback to 96 if it returns 0).
3. Compute `sb_height = dpi_scale(24)`.
4. Reflow path bar: `MoveWindow(state.drive_picker, dpi_scale(8), path_bar_y, dpi_scale(80), dpi_scale(32))`; `MoveWindow(state.path_edit, dpi_scale(8 + 80 + 4), path_bar_y, client_width - dpi_scale(8 + 80 + 4 + 8), dpi_scale(32))`.
5. Reflow status bar: `MoveWindow(state.status, 0, client_height - sb_height, client_width, sb_height)`; compute pane right-edges via `compute_status_parts(client_width, dpi)`; send `SB_SETPARTS`.
6. Adjust the existing tree-list HWND's vertical extent to end at `client_height - sb_height` (not `client_height - 30` as today — the status bar now occupies the bottom strip).
7. Existing reflow code for buttons, ribbon, etc. — unchanged.

**Constraint:** No more than one `MoveWindow` call per HWND per WM_SIZE — keeps the resize feel snappy on large windows.

## Don't-Do List for This Phase

These are visual or interaction patterns the executor MUST NOT introduce in Phase 2, to keep scope honest:

1. **No custom-painted status bar.** Use `msctls_statusbar32`. Custom painting is a Phase 8+ visualization concern; the status bar gets the common-control treatment now.
2. **No animation on focus / hover / selection.** Win32 themed defaults only. The web UI uses CSS transitions (`transition: all 0.2s cubic-bezier(...)`); the desktop equivalent is "instant repaint." Do not invent animation primitives this phase.
3. **No drive icons in the picker.** Text-only per the RESEARCH open question. Image-list integration is its own follow-up.
4. **No settings UI / preferences dialog.** Settings change through existing toolbar controls (dark-mode checkbox, hidden-files checkbox, column drag, window resize). Per CONTEXT deferred-ideas: "Settings UI / Preferences dialog — out of scope. Could be a polish task post-v1."
5. **No red destructive color anywhere.** Phase 5 introduces destructive UI with its own color contract; Phase 2 stops short.
6. **No tooltips on the status bar panes.** They're labeled inline (`"1,234 files"` is self-describing). A hover tooltip duplicating "files count" would be noise.
7. **No "Save settings" button or progress indicator.** Settings save is automatic and invisible per CONTEXT D-03; surfacing it would suggest the user has a choice.

## DPI Awareness Note (Carryover Pattern)

The existing app does not yet honor per-monitor DPI. Phase 2 introduces the `dpi_scale(value: i32) -> i32` helper in `src/desktop/ffi.rs` (wrapping `GetDpiForWindow`) and uses it for every new measurement in this contract. **This is the recommended landing point** for the DPI helper that Phase 8 visualizations will lean on heavily. Existing pre-Phase-2 measurements (toolbar buttons, ribbon, tree row heights in `paint.rs`) remain DPI-naive in this phase — retrofitting them is out of scope for Phase 2 and explicitly deferred. The helper exists; old code can adopt it incrementally in future phases.

Specifically:
- Path bar: DPI-scaled. ✓
- Status bar height + pane widths: DPI-scaled. ✓
- Drive picker width: DPI-scaled. ✓
- Existing toolbar/ribbon/tree: NOT scaled (out of scope). Acceptable visual mismatch at non-100% DPI for one phase.
